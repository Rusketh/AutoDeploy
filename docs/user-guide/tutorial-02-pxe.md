# Tutorial 2 — Set up PXE boot

20 minutes. After this, target machines on your network can PXE
boot to AutoDeploy. Covers **UniFi**, **dnsmasq**, **ISC dhcpd**,
**Microsoft DHCP** — pick the one that matches your environment.

Prerequisite: [Tutorial 1](tutorial-01-install.md) is done and the
server is running.

## What's about to happen

When a target machine powers on with PXE enabled in firmware:

1. It broadcasts a DHCP request asking for both an IP and a boot
   file.
2. Your DHCP server hands back an IP + the address of a TFTP
   server + the name of a "first-stage" boot file.
3. The machine TFTP-fetches the first-stage boot file. We use
   **iPXE** — a small ~75 KB / 1 MB binary that knows how to boot
   over HTTP. Use a **stock, unmodified** iPXE binary — from
   `boot.ipxe.org`, AutoDeploy's CI release, or your distro. No
   custom build required (see the box below).
4. The instant iPXE comes up it auto-fetches **`autoexec.ipxe`**
   from the same server it booted from. AutoDeploy serves this
   file automatically (over TFTP *and* HTTP), so the stock binary
   gets its instructions with nothing baked in.
5. `autoexec.ipxe` chainloads to `http://<autodeploy>/ipxe/boot.ipxe`,
   which fetches the Linux kernel + initramfs that runs the
   **Boot Client**.
6. The Boot Client identifies the machine to AutoDeploy, picks an
   image, deploys.

> **You do not need to build a custom iPXE.** Older guides told you
> to compile an iPXE binary with the server URL embedded. That's no
> longer necessary: AutoDeploy serves `autoexec.ipxe` itself, so any
> stock iPXE binary self-bootstraps. The embedded-build path
> (`build-embedded-ipxe.sh`) still exists for unusual setups, but
> it's the exception now, not the rule.

**So the whole DHCP job is just: hand out a stock iPXE binary.**
Point `next-server` (DHCP option 66) at the AutoDeploy host and set
the bootfile to the right binary for the client's firmware. That's
it — no conditional/two-stage DHCP, no user-class matching, no
embedded build. Those advanced patterns are still documented below
for mixed fleets, but you almost certainly don't need them.

## Step 1 — Make sure AutoDeploy is serving the boot files

The installer set this up. Verify:

```sh
sudo systemctl status autodeploy
journalctl -u autodeploy -n 50 --no-pager | grep tftp.listen
# Expect: tftp.listen addr=:69 root=/var/lib/autodeploy/ipxe

ls /var/lib/autodeploy/ipxe/
# undionly.kpxe     ← BIOS PXE chainload
# ipxe.pxe          ← BIOS PXE chainload, alternative if undionly.kpxe is flaky
# ipxe.efi          ← UEFI x64
# snponly.efi       ← UEFI x64 fallback (use if ipxe.efi can't bring NIC up)
# ipxe-arm64.efi    ← UEFI arm64
# (autodeploy-kernel and autodeploy-initrd land here after step 3 below)
```

If `ipxe.efi` and `snponly.efi` are missing, fetch them manually
from `http://boot.ipxe.org/x86_64-efi/` (see
[troubleshooting](troubleshooting.md#pxe)) or re-run
`sudo /etc/autodeploy/scripts/fetch-ipxe.sh` from the release
bundle.

Smoke-test the TFTP server from another box on the LAN. Grab a
binary **and** the synthesised bootstrap script:

```sh
tftp <autodeploy-ip>
tftp> get ipxe.efi
Received 1182208 bytes in 0.1 seconds
tftp> get autoexec.ipxe
Received 612 bytes in 0.0 seconds
tftp> quit
```

`autoexec.ipxe` is **generated by the server** — you won't see a
file by that name in `/var/lib/autodeploy/ipxe/`, but TFTP (and
`http://<autodeploy>/autoexec.ipxe`) hand it back on demand. This
is what lets a stock iPXE binary bootstrap with nothing embedded.
If both round-trip, the AutoDeploy side is ready.

## Step 2 — Configure DHCP

The simple path works on **any** DHCP server, including UniFi and
consumer routers: hand out a stock iPXE binary and point clients at
the AutoDeploy host. iPXE fetches `autoexec.ipxe` from there and
bootstraps itself.

- **Single-firmware fleet (the common case):** jump to
  [Step 2A — point DHCP at one binary](#step-2a---point-dhcp-at-one-binary).
  This is what UniFi / OPNsense / consumer-router users want.
- **Mixed BIOS + UEFI on one VLAN:** you need DHCP to pick the
  bootfile per client architecture — see
  [Step 2B — per-arch DHCP](#step-2b---per-arch-dhcp-isc--microsoft--kea--dnsmasq).
  (You still don't need user-class matching or an embedded build;
  `autoexec.ipxe` handles the chainload.)

BIOS clients want `undionly.kpxe`, UEFI x64 clients want `ipxe.efi`
(or `snponly.efi`), UEFI arm64 clients want
`ipxe-arm64.efi`, all on the same network.

## Step 2A — Point DHCP at one binary

The common case, and all most setups ever need. Hand out one stock
iPXE binary and point clients at the AutoDeploy host. iPXE fetches
`autoexec.ipxe` from the server and bootstraps itself — no
conditional DHCP, no user-class matching, **no custom build.**

### Configure UniFi

UniFi has a built-in "Network Boot" feature. You only need it to
hand out the binary and point at the server.

**Where the setting is:**

| UniFi controller | Path |
|---|---|
| UniFi Network 8.x (UDM-Pro, UDR, UCG-Max, Cloud Gateway Ultra) | Settings → Networks → *[your LAN]* → **Advanced** → DHCP Service → **Network Boot** |
| UniFi Network 7.x and older | Settings → Networks → *[your LAN]* → **DHCP** → Network Boot |

**Fields:**

| Field | Value |
|---|---|
| Enable Network Boot | **on** |
| Next Server | LAN IP of your AutoDeploy host (e.g. `192.168.1.5`) |
| Boot File | depends on the fleet — see below |

**Boot file by fleet:**

| Fleet | Boot File |
|---|---|
| Modern UEFI x64 (~2015+, most homelab gear) | `ipxe.efi` |
| UEFI x64 where `ipxe.efi` can't bring the NIC up | `snponly.efi` |
| Legacy BIOS | `undionly.kpxe` |
| Hyper-V Gen2 specifically | `snponly.efi` (Hyper-V's synthetic NIC prefers SNP-only) |

UniFi only accepts ONE boot file per network. Mixed fleets need
either separate VLANs or the [dnsmasq proxy](#mixed-fleets-on-unifi---dnsmasq-as-proxy)
approach below.

### Other single-bootfile DHCP servers (same pattern)

The pattern is the same on any DHCP server: set `next-server` to
the AutoDeploy IP, `bootfile` to whichever iPXE binary matches
your fleet.

| DHCP server | Where |
|---|---|
| OPNsense / pfSense | Services → DHCPv4 → *[interface]* → Network Booting |
| OpenWrt | LuCI → Network → DHCP and DNS → "TFTP server" section |
| MikroTik RouterOS | IP → DHCP Server → Network → fill `next-server` and `boot-file-name` |

### Mixed fleets on UniFi — dnsmasq as proxy

UniFi UI gives ONE boot file per network. If you have BIOS +
UEFI on the same VLAN and don't want to split VLANs, run
dnsmasq in **proxy-DHCP mode** alongside UniFi:

```ini
# /etc/dnsmasq.d/autodeploy.conf
dhcp-range=192.168.1.0,proxy
dhcp-no-override
dhcp-match=set:bios,option:client-arch,0
dhcp-match=set:uefi64,option:client-arch,7
dhcp-match=set:uefi64,option:client-arch,9
dhcp-match=set:uefiarm,option:client-arch,11
dhcp-boot=tag:bios,undionly.kpxe,,192.168.1.5
dhcp-boot=tag:uefi64,ipxe.efi,,192.168.1.5
dhcp-boot=tag:uefiarm,ipxe-arm64.efi,,192.168.1.5
```

Replace `192.168.1.0` with your subnet, `192.168.1.5` with the
AutoDeploy host. UniFi keeps doing IP leases; dnsmasq just picks
the per-arch binary. No `user-class iPXE` branch needed —
`autoexec.ipxe` handles the HTTP chainload.

## Step 2B — Per-arch DHCP (ISC / Microsoft / Kea / dnsmasq)

For mixed BIOS + UEFI fleets on one VLAN. The only job here is
picking the right iPXE binary per client architecture — once iPXE
loads, `autoexec.ipxe` takes over the HTTP chainload, so you do
**not** need a `user-class iPXE` branch.

These configs use the **prebuilt** stock iPXE binaries — no
embedded build.

> **Note:** Older versions of this guide used a "two-stage"
> config with an `if user-class = "iPXE"` branch that handed iPXE
> clients an HTTP URL directly. That still works, but it's
> redundant now: `autoexec.ipxe` does the chainload, so the
> simpler per-arch config below is all you need.

### ISC dhcpd

```
# /etc/dhcp/dhcpd.conf
option arch code 93 = unsigned integer 16;

subnet 192.168.1.0 netmask 255.255.255.0 {
    range 192.168.1.100 192.168.1.200;
    option routers 192.168.1.1;
    next-server 192.168.1.5;   # AutoDeploy (TFTP + autoexec.ipxe)

    if option arch = 00:07 or option arch = 00:09 {
        filename "ipxe.efi";
    } elsif option arch = 00:0b {
        filename "ipxe-arm64.efi";
    } else {
        filename "undionly.kpxe";
    }
}
```

Restart: `sudo systemctl restart isc-dhcp-server`.

### Microsoft DHCP

DHCP console → right-click the scope → **Configure Options** →
**Advanced** tab:

| Option | Value |
|---|---|
| 066 (Boot Server Host Name) | AutoDeploy IP |
| 067 (Bootfile Name) | `ipxe.efi` |

For arch-based and iPXE-class branching, create Vendor Classes
matching the client's DHCP option 60/93 and override option 067
per class. Microsoft's how-to:
<https://learn.microsoft.com/en-us/windows-server/networking/technologies/dhcp/dhcp-pxe-boot>.

### dnsmasq (full DHCP, not proxy)

```ini
# /etc/dnsmasq.d/autodeploy.conf
dhcp-range=192.168.1.100,192.168.1.200,12h
dhcp-match=set:bios,option:client-arch,0
dhcp-match=set:uefi64,option:client-arch,7
dhcp-match=set:uefi64,option:client-arch,9
dhcp-match=set:uefiarm,option:client-arch,11
dhcp-boot=tag:bios,undionly.kpxe,,192.168.1.5
dhcp-boot=tag:uefi64,ipxe.efi,,192.168.1.5
dhcp-boot=tag:uefiarm,ipxe-arm64.efi,,192.168.1.5
```

## Step 3 — Drop the Boot Client kernel + initramfs in place

iPXE chainloads to AutoDeploy's `http://<host>/ipxe/boot.ipxe`,
which references the kernel + initramfs. Build the initramfs
once:

```sh
sudo /etc/autodeploy/scripts/initramfs/build-initramfs.sh
sudo cp /boot/vmlinuz-$(uname -r) /var/lib/autodeploy/ipxe/autodeploy-kernel
sudo chown autodeploy:autodeploy /var/lib/autodeploy/ipxe/autodeploy-kernel
```

For production, build a small specialised kernel — see the
`scripts/initramfs/` README.

## Step 4 — PXE boot a target machine

Power on. You should see:

```
PXE Boot
Querying DHCP...     [ok]
Loading boot image...
iPXE 1.21.1+ -- Open Source Network Boot Firmware
=== AutoDeploy bootstrap ===        <- from the served autoexec.ipxe
Configuring (net0...) ok
Chainloading from 192.168.20.60 ...
[kernel + initramfs download]
[AutoDeploy boot menu]
```

If you get there, you're done. Move on to [Tutorial 3 — Deploy
your first machine](tutorial-03-first-deploy.md).

## UEFI HTTP Boot (no TFTP, modern firmware only)

UEFI 2.5+ firmware (PCs from ~2017 onwards) can skip TFTP
entirely. Hand HTTPBoot clients the iPXE binary over HTTP; once it
loads it fetches `autoexec.ipxe` over HTTP from the same server
(AutoDeploy serves it at `/autoexec.ipxe`) and bootstraps exactly
as the TFTP path does:

```
# ISC dhcpd
class "uefi-httpboot" {
    match if substring(option vendor-class-identifier, 0, 10) = "HTTPClient";
    option vendor-class-identifier "HTTPClient";
    filename "http://192.168.1.5:8080/ipxe/static/ipxe.efi";
}
```

UniFi: not in the UI; use dnsmasq alongside.

## If something doesn't work

See [Troubleshooting → PXE](troubleshooting.md#pxe-boot). The
most common ones:

| Symptom | Probable cause |
|---|---|
| Machine never picks up a boot file | DHCP option 66/67 missing or wrong; firewall blocking TFTP (UDP/69). |
| iPXE loads then sits at `Configuring (net0...)` with `autoexec.ipxe... Not found` | The server isn't serving `autoexec.ipxe`. Confirm `next-server`/option 66 points at the AutoDeploy host and `tftp <host>` / `get autoexec.ipxe` round-trips. (This needs AutoDeploy ≥ the release that added served `autoexec.ipxe`.) |
| `iPXE: No more network devices` | NIC driver issue. Swap `ipxe.efi` for `snponly.efi`. |
| TFTP says ENOTFOUND for ipxe.efi | The binary isn't in `/var/lib/autodeploy/ipxe/`. Re-run `fetch-ipxe.sh` (any stock iPXE binary works). |
| iPXE chainloads but the HTTP fetch fails | Firewall, or HTTPS with a self-signed cert iPXE doesn't trust. Use plain HTTP for the bootfile URL. |
